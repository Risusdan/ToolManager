# ToolManager 作者手冊

給寫工具、要把工具上架到 ToolManager 的同仁。一般使用方式請看[使用手冊](USER_GUIDE.md)。

## 1. 開始之前

- **需要 catalog repo 的寫入權限**：ToolManager 只對有寫入權限的帳號顯示發布功能（側欄底部的「上架新工具」）。看不到的話，請向管理員申請加入工具開發人員群組。
- **不需要會 git**：發布精靈會幫你上傳檔案、建立 branch 與 Pull Request。
- **審核規則**：

  | 情況 | 結果 |
  |---|---|
  | 上架新工具 | 送出後等管理員核准 Pull Request，核准後上線 |
  | 你負責的工具發布新版本 | 立即合併上線 |
  | 你不是 owner 的工具 | 無法發布新版本（管理員除外） |

## 2. 準備程式

先決定工具類型：

| 類型 | 適用 | 要準備的內容 |
|---|---|---|
| **執行檔** | 免安裝、解壓就能執行的程式 | 程式資料夾（含 `.exe` 與所需的 DLL、設定檔） |
| **Python 腳本** | `.py` 腳本 | 程式資料夾（含進入點，例如 `main.py`），需要第三方套件時附上 `requirements.txt` |
| **安裝程式** | 必須安裝的程式（setup.exe、.msi） | 安裝程式本身；ToolManager 只負責下載並開啟它 |

- **zip 或資料夾都可以**：精靈會自動把資料夾打包成 zip，並略過 `__pycache__`、`.venv`、`.git` 等暫存資料夾。
- **zip 裡多包了一層資料夾也沒關係**（例如 `MyTool/MyTool.exe`），安裝時會自動攤平。
- **執行檔工具會被解壓到使用者的電腦上執行**：程式要能在自己的資料夾內寫入檔案（設定、log），不要假設會裝在 `C:\Program Files`。

### Python 腳本的注意事項

- ToolManager 附帶 Python 3.12，使用者不需要自己安裝。如果需要特定版本，`release.toml` 的 `python` 欄位可以寫版本需求，例如 `>=3.11`；發布新版本時會沿用上一版的設定。
- 第三方套件寫在 `requirements.txt`，第一次執行時 ToolManager 會從部門的 PyPI mirror 安裝，每個工具版本各有獨立的環境。
- 如果工具也要**給客戶**，客戶連不到內部 mirror，zip 裡必須附上 `wheels\`。在 Windows 上執行：

  ```powershell
  pip download -r requirements.txt -d wheels --only-binary=:all: --platform win_amd64 --python-version 3.12
  ```

- 用 `argparse` 接參數的腳本，可以在精靈中設定**參數表單**（見 4.3），使用者就能用表單填值，不用打指令。
- 會開啟自己視窗的腳本（tkinter、PySide 等），勾選「有自己的視窗」，就不會多跳一個主控台。

## 3. 寫 README

README 會顯示在工具詳情頁，是使用者認識工具的第一站，也能大幅減少「這怎麼用」的詢問。建議包含：

- 這個工具做什麼、適合什麼情境（第一段）
- 主畫面截圖
- 基本使用步驟
- 常見問題

圖片放在程式資料夾內（例如 `assets/main.png`），README 中這樣寫：

```markdown
![主畫面](assets/main.png)
```

規則：
- 只能引用工具資料夾內的圖片，每張最多 2 MB。
- 網路上的圖片（`https://…`）可以使用，但使用者必須連得到那個網址。

## 4. 用發布精靈發布

- **新工具**：側欄底部「上架新工具」。
- **新版本**：工具詳情頁「版本歷史」旁的「發布新版本」。只有該工具的 owners 和管理員看得到。

精靈只有一頁，分四個區塊。

### 4.1 程式
在路徑欄貼上 zip 檔或資料夾的路徑，或按「選擇 zip…」/「選擇資料夾…」。下方會顯示檔案數量。

### 4.2 工具資料
| 欄位 | 說明 |
|---|---|
| 工具 ID | 小寫英文、數字與 `-`，例如 `register-viewer`。**發布後不能更改** |
| 類型 | 執行檔 / Python 腳本 / 安裝程式 |
| 名稱、分類 | 顯示在工具目錄中 |
| 摘要 | 工具卡片上的一句話 |
| 擁有者 | Bitbucket 帳號，以逗號分隔。只有擁有者能發布新版本，建議至少兩位，避免一個人休假時無人能修 |
| 問題回報連結 | 選填，目前只記錄在 `tool.toml`；使用者回報問題一律走部門共用的 Jira |
| README | Markdown，見第 3 節 |

發布新版本時，這些欄位會自動帶入目前的內容。有修改才會一起提交。

### 4.3 版本與參數
- **版本**：格式為 `主版本.次版本.修訂`（例如 `1.2.0`），必須大於目前最新版。精靈預設為下一個修訂號。
  - 修 bug：修訂號 +1（`1.2.0` → `1.2.1`）
  - 加功能：次版本 +1（`1.2.1` → `1.3.0`）
  - 不相容的大改：主版本 +1
- **啟動的檔案**：從套件中選擇（`.exe`、`.py` 等），精靈通常會自動猜到。
- **更新說明**：條列這版改了什麼，會顯示在「版本歷史」中。例如：

  ```
  - 新增：設定檔差異比較
  - 修正：大檔案開啟時當機
  ```

- **建議盡快更新**：只用在使用者「應該馬上更新」的情況（嚴重錯誤、資料錯誤）。勾選後要用一句話說明原因，會以醒目方式顯示給使用者。不要每版都勾，否則提示會失去意義。
- **參數（Python 腳本）**：每個參數一列：

  | 欄位 | 說明 |
  |---|---|
  | 名稱 | 命令列用的名稱；預設對應 `--名稱 值` |
  | 表單上的標籤 | 使用者看到的文字 |
  | 類型 | 文字、整數、數字、勾選框、檔案、資料夾、下拉選單 |
  | 預設值、說明 | 選填 |
  | 必填 | 使用者必須填寫 |
  | 位置參數 | 只傳值、不加 `--名稱`，依參數順序排列 |
  | 命令列旗標 | 不想用 `--名稱` 時自訂，例如 `-i` |

  下方的「執行頁預覽」會顯示使用者實際看到的表單，以及預設值對應的命令列。發布新版本時會沿用上一版的參數。

### 4.4 檢查與發布
1. 按「**檢查**」。精靈會用和合併前相同的規則檢查：
   - 必填欄位
   - 版本號是否大於最新版
   - 套件內是否有啟動的檔案
   - README 圖片是否存在且不超過大小
   - 你是否為擁有者
2. 紅色是錯誤，必須修正；琥珀色是提醒；灰色是給審核者的說明（例如「新工具，需管理員核准」）。
3. 沒有錯誤後按「**發布**」，確認後會依序上傳套件、提交檔案、建立 Pull Request。
4. 結果：
   - **新版本**：顯示「已發布」，同事下次同步時就會看到（預設每 4 小時一次，也可以從系統匣選「檢查更新」立即同步）。
   - **新工具**：顯示「已送出審核」並附 Pull Request 連結，管理員核准後上線。
   - **無法自動合併**：例如同時有人發布了同一個版本，會顯示原因並保留 Pull Request。請開啟連結處理，或通知管理員。

## 5. 發布後

- **出問題時**：使用者可以在詳情頁「⋯」→「切換回」回到上一版；你則發布一個修正版（修訂號 +1）。
- **已發布的版本不能修改**：要改內容就發新版本。這是為了讓已安裝的同事、回退功能都能信任每個版本號代表固定的內容。
- **問題回報**：使用者回報的問題會帶有 `tm-<工具 ID>` 標籤，在 Jira 中用這個標籤篩選就能看到你的工具的所有問題。
- **交接**：在發布新版本時修改「擁有者」欄位即可。

## 6. 進階：不用精靈，直接改 catalog repo

熟悉 git 的作者也可以直接在 catalog repo 開 branch 修改，再發 Pull Request。目錄結構：

```
tools/<工具 ID>/
  tool.toml                    名稱、摘要、分類、擁有者、類型
  README.md
  assets/                      README 的圖片
  releases/<版本>/
    release.toml               版本、日期、啟動檔、更新說明、參數
    <工具 ID>-<版本>.zip         以 Git LFS 儲存
```

送 Pull Request 前，先在本機用和精靈相同的規則檢查：

```powershell
uv run python scripts\check_catalog.py <catalog repo 資料夾> --base origin/main --author <你的帳號>
```

欄位的完整說明請見 `docs/DESIGN.md` §3。
