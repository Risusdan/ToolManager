## 2. Bitbucket Server API

先在 Bitbucket 建立一個**測試用** catalog repo，把 `examples\catalog` 的內容推上去，並用 Git LFS 加入至少一個 zip，例如：

```powershell
git lfs track "tools/*/releases/*/*.zip"
# 放一個任意 zip 到 tools\register-viewer\releases\1.1.0\register-viewer-1.1.0.zip
```

接著執行（腳本為唯讀，不會寫入伺服器）：

```powershell
$env:TOOLMANAGER_TOKEN = "<個人 HTTP access token>"
uv run python scripts\p0_check_bitbucket.py --url https://<bitbucket 網址> `
    --project <PROJECT> --repo <catalog repo> `
    --artifact tools/register-viewer/releases/1.1.0/register-viewer-1.1.0.zip
```

| # | 檢查項目 | 若失敗的備案 |
|---|---|---|
| 2.1 | REST commits API 取得最新 revision、取得使用者名稱 | 確認 token 權限（需 repo read） |
| 2.2 | archive API 下載 catalog zip | 改用 REST browse API 逐檔下載 |
| 2.3 | archive 中 LFS 檔案維持為指標檔（不含實際內容） | 改用 archive API 的 `path` 參數只抓 manifest 相關路徑 |
| 2.4 | catalog 解析成功 | 修正 manifest |
| 2.5 | raw + LFS batch API 下載並通過 sha256 驗證 | 確認 LFS 是否啟用；改用 Bearer 認證 |

另外請記下 Bitbucket 頁尾顯示的**版本號**。

### 2a. 發布（寫入 API）

**先跑腳本**（會寫入伺服器，只能用**測試** repo；token 需 repo write 權限）。每次執行會以新的版本號發布一個假工具 `p0-publish-check`，逐步驗證精靈用到的每個 API：

```powershell
$env:TOOLMANAGER_TOKEN = "<有寫入權限的 token>"
uv run python scripts\p0_check_publish.py --url https://<bitbucket 網址> `
    --project <PROJECT> --repo <測試 repo> --confirm <測試 repo>
```

| # | 步驟 | 失敗時的備案 |
|---|---|---|
| 1 | 帳號與寫入權限（`repos?permission=REPO_WRITE`） | 改以 catalog 名單判斷開發人員 |
| 2 | 取得目標分支最新 commit | 同 2.1 |
| 3 | Git LFS 上傳（batch、PUT、verify） | 確認 repo 已啟用 LFS；記下錯誤訊息 |
| 4 | 從指定 commit 建立 branch（`POST .../branches`） | 改用 `branch-utils` API，或 browse API 的 `sourceBranch` |
| 5 | 逐檔 commit 新檔案（browse API `PUT`） | 記下 HTTP 狀態與訊息 |
| 6 | 修改既有檔案（409 後以 `sourceCommitId` 重送） | 記下訊息；可能需改用 commit 前先取得檔案的最後 commit |
| 7 | 從 branch 下載套件並比對 sha256（raw + LFS） | 同 2.5 |
| 8 | 開 Pull Request | 記下訊息 |
| 9 | 合併 Pull Request | 若訊息為需要核准，屬預期行為（精靈會保留 PR）；可加 `--no-merge` 只測到第 8 步 |

全部 PASS 後，再用 ToolManager 介面實際操作一次：

| # | 操作 | 通過標準 | 若失敗的備案 |
|---|---|---|---|
| 2a.0 | 分別用有、沒有 repo 寫入權限的帳號開啟 ToolManager | 有權限：側欄底部出現「上架新工具」；沒權限：不出現，開 `/publish` 顯示「發布功能只開放給工具開發人員」 | `repos?permission=REPO_WRITE` 不可用時改以 catalog 名單判斷 |
| 2a.1 | 在 `register-viewer` 詳情頁按「發布新版本」，選一個資料夾，填更新說明後發布 | 顯示「已發布」；repo 出現 branch `publish/register-viewer-<版本>`、Pull Request 已合併；新 zip 在 Bitbucket 顯示為 LFS 檔案 | 依錯誤訊息：LFS 上傳失敗→確認 LFS 已啟用；branch 建立失敗（404）→改用 `branch-utils` API 或 browse API 的 `sourceBranch` |
| 2a.2 | 同一頁改摘要後再發布一次 | `tool.toml` 的修改成功（測試 browse API 以 `sourceCommitId` 修改既有檔案） | 回報錯誤訊息 |
| 2a.3 | 側欄「上架新工具」，填一個新工具並發布 | 顯示「已送出審核」，Pull Request 保持開啟 | — |
| 2a.4 | `main` 設定「需 1 位核准」後再發布新版本 | 顯示「Pull Request 已建立，但無法自動合併：…」並附連結 | — |
| 2a.5 | 用沒有寫入權限的帳號發布 | 顯示「你的帳號沒有 catalog repo 的寫入權限」 | — |

> 發布用的「REST API 建立 commit」需要寫入權限，會在 P3 前另外以測試 repo 驗證。

## 2b. Jira（回報問題）

在瀏覽器（已登入 Jira）開啟以下網址，取得 `catalog.toml` 的 `[jira]` 需要的數字 ID：

| 項目 | 網址 | 取用欄位 |
|---|---|---|
| `project_id` | `https://<jira>/rest/api/2/project/<PROJECT_KEY>` | `"id"` |
| `issue_type_id` | `https://<jira>/rest/api/2/project/<PROJECT_KEY>`（同一頁的 `issueTypes`） | Bug 那一項的 `"id"` |

填入後在 ToolManager 點「回報新問題」，確認 Jira 建單頁的專案、類型、label（`tm-<工具 id>`）與描述都已預先填好；「查看已知問題」能列出該 label 的 ticket。
